# 작업 접수 — 말 → 의도 계약 → 지시서 → 투입

원 구상의 ① 음성으로 직관적 입력, ② 사전 검토와 인터뷰로 최선의 최종 프롬프트를 맡는 정방향 조각이다.
사람이 승인하는 것은 **계약**이고(P1), 워커가 받는 것은 계약에서 컴파일한 **지시서 한 장**이다.
개념은 `docs/concept.md`, 표면 근거는 `docs/architecture.md`. 완성된 예는 `examples/rambling-request.md`.

## 불변 규칙

1. **원문을 보존한다.** 받아쓰기 그대로 적어 두고 지시서 부록으로 붙인다. 정리본과 원문을 나란히 둔다.
2. **묻기 전에 알아낸다.** 스스로 확인할 수 있는 것은 묻지 않는다. 사람만 아는 것만, 질문마다 추천 기본값과 함께(P3).
3. **승인 전에는 투입하지 않는다.** 비가역·외부 공개·큰 비용이 걸리면 말 한마디 "네"가 아니라 칩으로 고르게 한다(P9).
4. **단계가 아니라 의도로 지시한다(P2).** 사용자가 정하지 않은 "어떻게"는 워커에게 맡긴다.
5. **한국어로 묻고 쓴다**(식별자·코드 제외).
6. **계약·지시서는 이 리포에 커밋하지 않는다** — 공개 리포다. 계약은 워커 세션의 지시서 안에 산다(D-015).

## 절차

### 1. 받기

- 원문을 그대로 적어 둔다. 말 더듬·반복·생각 말하기는 걷어 내되 뜻은 바꾸지 않는다.
- 요청이 여러 개 섞였으면 갈라서 보인다: "요청 A … / 요청 B …(따로 접수할까요?)".
- 한 줄로 되말한다: `요지: …` — 질문이 아니라 표시다. 틀렸으면 사용자가 끊는다.

### 2. 깊이 고르기 — 한 단어로 알린다

| 깊이 | 언제 | 하는 일 |
|---|---|---|
| L0 통과 | 대상·결과가 한 문장으로 분명하고 되돌리기 쉽다 | 인터뷰 없이 지시서 → 확인 1회 |
| L1 다듬기 | 의도는 분명한데 완료 기준·제약이 조금 빈다 | 기본값으로 채우고 가정 목록만 보여 준다 |
| L2 인터뷰 | 목표·범위가 모호하거나 되돌리기 어렵다 | 질문 1묶음(최대 4개, 크면 2묶음) → 계약 |
| L3 운영 | L2이면서 길고 이정표가 여럿이다 | L2 + 체크포인트 계획 |

### 3. 사전 검토 — 묻기 전에 알아낸다

- **대상 리포**: 원문에서 찾고, 모호하면 `list_repos`(query)로 후보를 좁힌다. 둘 이상 남을 때만 묻는다.
- **겹치는 세션**: `list_sessions` 후 리포 루트에서
  `python3 -I .claude/skills/assis-inbox/scripts/triage.py <저장경로> --exclude <자기id>`.
  같은 리포에서 같은 일을 하는 세션이 있으면 "새 세션 대신 그 세션에 전달"을 선택지에 넣는다.
- **대상의 규칙**: 필요하면 대상 리포의 README·CLAUDE.md만 읽는다(`add_repo` read → 파일 읽기). 코드 탐색은 워커 몫이다.
- 알아낸 것은 계약의 `맥락`에 근거 표기와 함께 적는다.

### 4. 인터뷰 — L2·L3만

묻는 순서: 목표·이유 → 완료 기준(무엇으로 확인하나) → 범위 밖 → 결정권(혼자 정해도 되는 것 / 꼭 물어야 하는 것) → 우선순위·기한.

- `AskUserQuestion`, 추천을 첫 선택지에 `(추천)`. 이미 아는 것·원문에 있는 것은 묻지 않는다.
- 답이 원문과 부딪히면 숨기지 말고 한 줄로 짚는다.
- 예산을 넘기면 남은 모호함은 `가정`으로 적고 진행한다. 질문을 더 늘리지 않는다.

### 5. 의도 계약 — 사람이 승인하는 유일한 것

`templates/contract.md` 양식으로 채운다. 화면에는 계약 전체, 🔊 한 줄은 "목표 한 줄 — 이대로 맡길까요?".

- **가정 목록을 반드시 보인다**(의도 표류 대응).
- `AskUserQuestion`: 승인(추천) / 고쳐서(말로) / 보류. 고친 내용은 반영하고 버전을 올린다(v1 → v2).
- 말로 고친 내용은 한 줄로 되읽고 반영한다(피드백은 대화가 아니라 계약 수정이다, P8).

### 6. 컴파일 — 지시서

`templates/worker-prompt.md` 양식으로 계약을 워커용 지시서로 바꾼다.

- 맥락(왜)을 먼저, 끝 상태와 검증 방법은 분명하게. 결정권·체크포인트에서 "멈추고 보고"를 명시한다.
- 보고 형식을 정해 준다: 결과 먼저 → 필요한 결정 1~2개(선택지와 추천) → 증거.
  이렇게 해 두면 세션 브리핑(`assis-inbox`)이 그대로 결정 카드로 옮긴다.
- 계약 블록을 지시서 안에 원본 그대로 넣고, 원문은 맨 끝 부록으로 — "어긋나면 계약을 따르고 어긋남을 보고".

### 7. 투입

- `create_session`(`source_url`=대상 리포, `prompt`=지시서, `title`=목표 요지, `tags`=`["dj-assis:intake"]`).
- 세션 링크와 "언제 무엇이 올라올지(체크포인트)" 한 줄을 알린다. 결과는 사용자가 "브리핑"을 부를 때 카드로 온다.
- 도구가 없거나 실패하면 멈추고 그대로 알린다. 대안: 지시서를 코드 블록으로 주고 Code 탭에 붙여 넣게 한다.

### 8. 기록 — 시험 기간

`trials/TEMPLATE.md`를 복사해 익명으로 남긴다(D-003·D-010): 깊이, 질문 수, 계약 고친 횟수, 투입 여부, 판정.
계약·지시서·원문은 기록에 옮기지 않는다.

## 하지 않는 것

- 직접 구현하지 않는다(워커 몫).
- 승인 없이 투입하거나, 계약에 없는 범위를 지시서에 넣지 않는다.
- 사용자의 원문을 고쳐 쓰지 않는다.
